/custom-code-review — ревью на баги
Задача: найти в изменениях то, из-за чего код поведёт себя неправильно. Это баги логики, сломанные контракты, проблемы с ошибками, конкурентностью, безопасностью и данными. Файлы ты не меняешь (кроме режима --fix). Стиль и упрощения сюда не относятся, для них есть /custom-simplify.

Код, который написала модель, чаще всего ломается в трёх местах. Он вызывает API, которого нет. Он меняет контракт и не обновляет места вызова. Он ослабляет тесты, чтобы они проходили. Эти три места проверяй всегда, даже в режиме quick.

Ценность ревью держится на доверии. Одна ложная находка заставляет перепроверять все остальные, и ревью перестают читать. Поэтому у каждой находки должен быть конкретный сценарий, который ты проверил по коду. Три настоящих бага лучше десяти «возможно».

Аргументы
Текст после команды, в любом порядке:

Что ревьюить. Номер или URL PR, ветка, диапазон коммитов A..B, HEAD~3..HEAD, staged, пути к файлам или папкам. Без указания берутся все изменения текущей ветки относительно основной: коммиты, staged, unstaged и новые неотслеживаемые файлы.
Глубина. quick, deep или ничего (обычная).
--comment — после ревью опубликовать находки комментариями в PR.
--fix — после ревью исправить подтверждённые находки.
Свободный текст — фокус («особенно проверь миграции»). Ставь его в приоритет, но остальные линзы не выключай.
Шаг 1. Собери изменения
Работай из корня репозитория. Команда ниже находит базу и делает снимок рабочего дерева вместе с новыми файлами, не трогая ни index, ни stash пользователя:

```bash

cd "$(git rev-parse --show-toplevel)" && GITDIR=$(git rev-parse --absolute-git-dir)
BASE=""; for b in "$(git symbolic-ref -q --short refs/remotes/origin/HEAD)" origin/main main origin/master master; do
  [ -n "$b" ] && git rev-parse -q --verify "$b^{commit}" >/dev/null && BASE=$(git merge-base HEAD "$b") && break; done
BASE=${BASE:-HEAD}
cp "$GITDIR/index" "$GITDIR/review.index"
TREE=$(GIT_INDEX_FILE="$GITDIR/review.index" git add -A && GIT_INDEX_FILE="$GITDIR/review.index" git write-tree)
rm -f "$GITDIR/review.index"; echo "BASE=$BASE TREE=$TREE"
git log --oneline "$BASE"..HEAD; git diff --stat "$BASE" "$TREE"
Переменные между вызовами shell не сохраняются, поэтому дальше подставляй выведенные хеши: git diff <BASE> <TREE>, git diff -W <BASE> <TREE> -- <путь> (-W показывает функции целиком), git show <BASE>:<путь> (версия файла до изменений).

Для других вариантов:

PR: gh pr view <N> --json title,body,baseRefName,headRefOid,files,url и gh pr diff <N>. Если ветка PR не выгружена локально, сделай git fetch origin pull/<N>/head и читай файлы через git show FETCH_HEAD:<путь>.
Диапазон или коммит: git diff A B, git show <sha>.
Не git-репозиторий или просто файлы: ревьюй указанные файлы целиком.
Lock-файлы, сгенерированный, вендоренный и минифицированный код, снапшоты не читай построчно. Отметь только сам факт изменения (например, неожиданно появилась новая зависимость). Если изменений нет, скажи об этом и остановись. Если diff огромный (больше ~3000 строк), предупреди пользователя, начни с файлов с логикой и используй режим deep.

Шаг 2. Пойми намерение и контекст
Баг — это расхождение между тем, что код делает, и тем, что он должен делать. Поэтому сначала выясни, что он должен делать:

Намерение. Посмотри заголовок и описание PR, связанный issue (gh issue view), сообщения коммитов и то, что пользователь говорил в сессии. Сформулируй для себя в 1–2 предложениях, что должно делать изменение. Неясное намерение — не повод останавливаться: ревьюй, а сомнения вынеси в «Вопросы автору».
Правила проекта. Найди CLAUDE.md, AGENTS.md, CONTRIBUTING в корне и в папках изменённых файлов. Правило действует только на файлы в своей папке и ниже. Посмотри конфиги линтера, тайпчекера и CI, чтобы знать, что и так проверяется автоматически.
Файлы целиком. Читай изменённые файлы полностью или через git diff -W, а не только сами изменения. Многие баги сидят в стыке новой строки со старым кодом рядом.
Радиус поражения — главный источник багов, которых не видно в самом diff. Для каждой изменённой сигнатуры, возвращаемого значения, выбрасываемой ошибки, побочного эффекта, ключа конфига или env, колонки БД, поля API, имени события или ключа кеша найди все места использования (Grep) и проверь, что они обновлены и всё ещё правильны.
Тесты. Посмотри, какие тесты добавлены или изменены и какие существующие тесты покрывают изменённый код.
Шаг 3. Ищи проблемы по линзам
Пройди по всем линзам. Примеры в каждой — подсказки, а не полный список.

Логика и граничные случаи. Перевёрнутое условие, < вместо <=, ошибка на единицу. Не та переменная: копипаста, исправленная в одной ветке и забытая в соседней. Приоритет операторов. || вместо ?? при значениях 0, "", false. Пустая коллекция, null, один элемент, максимальный размер, отрицательные числа и ноль, юникод. Целочисленное деление, округление денег во float. Часовые пояса, переход на летнее время, границы дат. Сравнение строки с числом. Мутация аргумента или общего объекта. Ранний return, который пропускает очистку или отправку события. Пропущенный case. Якоря и экранирование в регулярках.
Вызовы, контракты и радиус поражения. Вызов того, чего нет: метода, опции, флага CLI, поля, переменной окружения, пути импорта, которых нет в проекте или в установленной версии библиотеки. Модели такое часто выдумывают, поэтому проверяй по исходникам или типам зависимости (node_modules, site-packages, go doc) и по lock-файлу, какая версия стоит. Вызывающие места не обновлены. Сменилось значение по умолчанию. Функция теперь может вернуть null или выбросить ошибку. Пропала гарантия порядка или сортировки. Нарушена обратная совместимость публичного API, HTTP, событий, сериализованных форматов, данных в кеше и очередях. Не проверены обе ветки feature-флага. Переименованная переменная окружения не обновлена в конфигах деплоя.
Ошибки и ресурсы. Проглоченная ошибка. Слишком широкий catch. Ошибка превращена в значение по умолчанию, которое выглядит как валидные данные. Потеряна исходная причина. Забыт await, промис оставлен без обработки. Не закрыты файлы, соединения, блокировки, подписки, таймеры, слушатели. Частичный сбой оставляет систему в несогласованном состоянии (записали A, упали на B). Повтор неидемпотентной операции. Сетевой вызов без таймаута.
Конкурентность и состояние. Гонки «проверил, потом сделал» (TOCTOU). Общее изменяемое состояние или кеш между запросами. Нет транзакции или неверные её границы. Двойная обработка сообщения из очереди. Двойной сабмит. Во фронтенде: устаревшие замыкания, неполные зависимости эффектов, обновление состояния после размонтирования.
Безопасность. Инъекции: SQL, shell, шаблоны, path traversal. Пользовательский ввод в путях и URL (SSRF). Сырой HTML (XSS). Нет проверки прав на объект по id (IDOR). Обход аутентификации. Секреты в коде, логах или текстах ошибок, персональные данные в логах. Небезопасная десериализация. Слабый random для токенов. Mass assignment (всё тело запроса пишется в модель). Опасные значения по умолчанию.
Данные и миграции. Необратимая миграция или потеря данных при drop или rename. Блокировка большой таблицы. NOT NULL без default на существующих строках. Забытый backfill. Нет индекса под новый запрос на горячем пути. Порядок деплоя: код читает колонку раньше, чем прошла миграция. Изменены значения enum, которые уже лежат в БД.
Производительность, только с реальным эффектом. N+1. Запрос без limit или пагинации. Вся таблица или файл загружается в память. O(n²) на данных, которые могут быть большими. Тяжёлая работа на горячем пути. Кеш не инвалидируется — это вопрос корректности, а не скорости. Сообщай, только если можешь назвать реалистичный объём данных, при котором это станет заметно.
Тесты. Тесты ослаблены, чтобы пройти: удалены или пропущены (.skip, xit, @pytest.mark.skip), смягчены assert, ожидаемое значение подогнано под новый результат, снапшоты обновлены без причины. Исправление бага без теста, который его воспроизводит. Тест проверяет мок, а не поведение. Тест проходит, даже когда код сломан: нет assert, потерян await, assert спрятан в try. Изменённое поведение не отражено в тестах. Тест нестабилен из-за времени, случайности или порядка. Общее «мало тестов» не пиши — только конкретный недостающий тест для конкретной рискованной ветки.
Правила проекта. Явные нарушения правил из CLAUDE.md и подобных файлов. Процитируй правило и проверь, что оно действует на этот файл. Если нарушение заглушено (eslint-disable, noqa с причиной), пропусти.
Соответствие намерению. Изменение делает не то, что заявлено. Исправлено одно из N одинаковых мест. Остались TODO, заглушки, захардкоженные тестовые значения, отладочные флаги, временно отключённые проверки.
Шаг 4. Проверь каждую находку
Для каждого кандидата:

Сценарий. Опиши конкретный вход или состояние, затем что делает код (проследи по строкам), затем что должно было произойти. Если конкретный сценарий не пишется, это не находка, а максимум вопрос автору.
Попробуй опровергнуть. Может, это уже обработано: валидацией выше, типами, ограничением БД, гарантией фреймворка, middleware, или вызывающий код никогда не передаёт такое значение. Может, так задумано: об этом сказано в описании PR, комментарии или тесте. Может, проблема была и раньше: сверь с git show <BASE>:<путь>. Такую проблему считай находкой, только если diff сделал её достижимой или хуже.
Подтверди запуском, если это дёшево. Подойдёт существующий тест, одноразовый скрипт или REPL, временный тест вне репозитория (или удали его после). Ничего с побочными эффектами не запускай: никаких миграций, записи по сети, продовых конфигов.
Поставь статус. «Подтверждено» — сценарий прослежен по коду или воспроизведён. «Вероятно» — сценарий реалистичен, но зависит от того, что проверить не удалось; назови, что именно. Остальное отбрось.
Не сообщай (это ложные срабатывания):

стиль, нейминг, форматирование, «можно проще» (это для /custom-simplify);
то, что ловят компилятор, тайпчекер или линтер, если они реально запускаются в CI;
старые проблемы, которых diff не касается (максимум три серьёзные в разделе «Вне изменений»);
гипотетику, которая требует невозможного входа, и «а вдруг в будущем»;
общие советы вроде «добавьте логирование» или «покройте тестами»;
изменения поведения, которые задача требует явно.
Одна проблема в нескольких местах — это одна находка со списком мест.

Глубина и параллельные агенты
quick: шаги 1–2 кратко (diff, изменённые файлы целиком, вызовы изменённых сигнатур), линзы 1, 2, 3, 5, проверка своими силами.
Обычная: всё по порядку, своими силами. Если diff больше ~500 строк или 10 файлов и есть инструмент запуска агентов, работай как в deep.
deep:
Сам сделай шаги 1–2 и составь бриф: намерение, хеши BASE и TREE с командами diff, список файлов, применимые правила с путями, найденные места использования изменённых контрактов.
Запусти в одном сообщении параллельно 3 агента (general-purpose). Каждому передай бриф и его линзы. Правки запрещены, каждая находка — с file:line, сценарием и ссылками на код-доказательства, без сценария находку не возвращать. Распределение: А — линзы 1 и 10; Б — линзы 2, 3, 4; В — линзы 5–9.
Объедини дубли. Для каждой находки уровня 🟠 и выше параллельно запусти независимого агента-скептика (если находок больше шести, давай одному агенту 2–3 находки). Дай ему только бриф и формулировку находки, без рассуждений автора, и поставь задачу опровергнуть её по коду. Он возвращает вердикт: «подтверждено», «опровергнуто» или «не уверен», с доказательствами.
Опровергнутые находки выкинь. «Не уверен» понизь до «Вероятно» или выкинь. Последнее слово за тобой: по каждой находке, которая идёт в отчёт, сам перечитай код.
Если инструмента для агентов нет, делай то же последовательно, а шаг скептика выполняй сам: перед включением каждой находки явно попытайся её опровергнуть.

Шаг 5. Отчёт
Пиши на языке пользователя, идентификаторы оставляй как в коде. Сортировка: по важности, внутри — по уверенности.

🔴 Блокер: потеря или порча данных, уязвимость, падение или неверный результат в основном сценарии, сломанные вызывающие места, опасная миграция.
🟠 Важно: неверное поведение в реалистичном неосновном сценарии, утечка ресурсов, гонка, отсутствие теста на рискованную ветку.
🟡 Стоит поправить: настоящий баг с малым эффектом или на редком граничном случае.
