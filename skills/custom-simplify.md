/custom-simplify — упрощение без изменения поведения
Цель: изменённый код становится короче и понятнее, а ведёт себя ровно так же, как раньше.

У кода от моделей две типичные болезни. Первая — переизобретение: свой хелпер, тип, константа или обёртка над клиентом, хотя в проекте или зависимостях это уже есть. Вторая — перестраховка и «расширяемость»: лишние проверки, try/catch, абстракции на будущее. Скилл находит это, применяет безопасные правки, прогоняет проверки и отчитывается.

Это не поиск багов. Исправление бага меняет поведение, поэтому замеченный баг не исправляй, а вынеси в отчёт и предложи /custom-code-review. Если упрощать код с багом, баг может стать короче и начать выглядеть намеренным. Поэтому лучший порядок такой: /custom-code-review, затем исправление багов, затем /custom-simplify, затем тесты.

Аргументы
Текст после команды, в любом порядке:

Что упрощать. Номер или URL PR, ветка, диапазон коммитов A..B, staged, пути к файлам. Без указания берутся все изменения текущей ветки относительно основной: коммиты, staged, unstaged и новые файлы.
--dry-run (или «только отчёт») — ничего не менять, выдать отчёт с предлагаемыми правками.
Свободный текст — фокус или ограничение, например «только переиспользование» или «не трогай публичный API».
Принципы
Они важнее любого чек-листа ниже.

Поведение не меняется. Под поведением понимается всё наблюдаемое: возвращаемые значения и их типы, выбрасываемые ошибки, побочные эффекты и их порядок, публичный API, логи и метрики, на которые могут опираться алерты. Если не уверен, что правка эквивалентна, не применяй её, а опиши.
Лучшая правка — удаление. Упрощение не должно добавлять новый слой. После правки кода должно стать меньше или столько же, но проще.
Понятность важнее краткости. Не превращай код в однострочники-головоломки, вложенные тернарники и цепочки из шести вызовов. Если правка короче, но читать её труднее, не делай её.
Как принято в проекте. CLAUDE.md и соглашения соседнего кода сильнее общих идиом языка. Новый код должен выглядеть так, будто его написал автор окружающего кода.
Только изменённый код. Код вне diff не трогай. Исключение одно: ты переиспользуешь существующую функцию, и ей нужна крошечная обратно совместимая доработка (необязательный параметр), которая не влияет на текущих вызывающих. Всё крупнее этого — предложение в отчёте.
Правило трёх. Не выделяй общую абстракцию, пока нет трёх копий. Две похожие функции по пять строк — это нормально.
Ничего не придумывай. «Код уже простой» — нормальный результат. Слабые находки ради объёма отчёта вредят.
Шаг 1. Собери изменения и сделай снимок
Работай из корня репозитория. Команда находит базу и снимает состояние рабочего дерева вместе с новыми файлами, не трогая index и stash пользователя:

```bash

cd "$(git rev-parse --show-toplevel)" && GITDIR=$(git rev-parse --absolute-git-dir)
BASE=""; for b in "$(git symbolic-ref -q --short refs/remotes/origin/HEAD)" origin/main main origin/master master; do
  [ -n "$b" ] && git rev-parse -q --verify "$b^{commit}" >/dev/null && BASE=$(git merge-base HEAD "$b") && break; done
BASE=${BASE:-HEAD}
cp "$GITDIR/index" "$GITDIR/simplify.index"
TREE=$(GIT_INDEX_FILE="$GITDIR/simplify.index" git add -A && GIT_INDEX_FILE="$GITDIR/simplify.index" git write-tree)
rm -f "$GITDIR/simplify.index"; echo "BASE=$BASE TREE=$TREE"
git diff --stat "$BASE" "$TREE"
Запомни оба хеша: переменные между вызовами shell не сохраняются.

git diff <BASE> <TREE> — что упрощаем.
TREE — снимок до твоих правок. По нему в конце покажешь только свой diff, отдельно от работы пользователя, и сможешь откатить отдельный файл: git show <TREE>:<путь> > <путь>.
Для PR используй gh pr diff <N> (упрощай, только если ветка PR выгружена локально, иначе работай в режиме --dry-run). Для диапазона — git diff A B. Если это не git-репозиторий, упрощай указанные файлы, а перед правкой копируй каждый в /tmp/custom-simplify/, чтобы его можно было откатить. Lock-файлы, сгенерированный и вендоренный код не упрощай. Если изменений нет, скажи об этом и остановись.

Шаг 2. Узнай проект
Без этого шага дубль не распознать. Потрать на него время:

Правила. CLAUDE.md, AGENTS.md, CONTRIBUTING в корне и в папках изменённых файлов.
Зависимости и версии. Открой манифест (package.json, pyproject.toml или requirements, go.mod, Cargo.toml, Gemfile, composer.json, pom.xml или build.gradle). Если подключены, например, lodash, date-fns, zod, pydantic, more-itertools, guava, самописный аналог их функции — находка. Проверь версию языка и рантайма (engines, requires-python, target в tsconfig, версия go) и не предлагай то, чего в этой версии нет.
Общий код. Найди папки вроде utils, helpers, lib, common, shared, core, hooks, constants, types, services, fixtures, factories и выпиши, что они экспортируют: rg -n --no-heading "^(export |def |class |func |pub (fn|struct|enum) )" <папки>
Соглашения. Открой 1–2 соседних файла рядом с изменёнными. Посмотри, как там обрабатывают ошибки, логируют, ходят в HTTP и БД, как называют вещи и раскладывают файлы, какие хелперы используют в тестах.
Шаг 3. Найди кандидатов
A. Переиспользование (главная линза)
Выпиши всё новое, что добавил diff: функции, методы, классы, хуки, компоненты, типы, константы, enum, регулярки, SQL, конфиги, обёртки над клиентами, тестовые фикстуры и хелперы. Для каждого ищи аналог:

По имени и синонимам: format/fmt/render/stringify, parse/decode/deserialize, get/fetch/load/read, is/has/check/validate, make/create/build, normalize/clean/sanitize, map/convert/to, retry, sleep/delay/wait, chunk/batch, group/uniq, debounce/throttle.
По характерным литералам: регулярки, форматы дат, тексты ошибок, URL и эндпоинты, имена полей, магические числа. Один и тот же литерал в двух местах почти всегда означает дубль.
По поведению: опиши в двух словах, что делает код, и поищи эти слова в именах и комментариях.
В стандартной библиотеке и уже установленных зависимостях.
По подозрительным именам: V2, _new, Enhanced, Improved, utils2, новый файл рядом со старым похожим. Обычно это значит, что надо было поправить старое, а не копировать.
Внутри самого diff: одинаковая логика в двух новых местах.
Самописная инлайн-логика, которую давно закрывает существующий хелпер: работа с путями и URL, форматирование дат и денег, чтение env, самодельные type guard, retry, deep clone и merge, groupBy, chunk, uniq, плюрализация.
Типы: новый интерфейс повторяет существующую модель, DTO или сгенерированный тип (из OpenAPI, GraphQL, ORM). Используй его или выведи из него (Pick, Omit, Partial).
Константы: магическое значение, которое уже есть в константах, enum или конфиге.
Тесты: собственный setup, хотя есть общие фикстуры и фабрики.
Найдя кандидата, открой его и сравни поведение: аргументы и значения по умолчанию, обработку null и пустых значений, бросает он ошибку или возвращает её, sync или async, часовой пояс и локаль, мутирует ли он данные или копирует, побочные эффекты (логи, метрики, кеш).

Поведение идентично — применяй.
Отличие есть, но в этом месте не проявляется (существующий хелпер обрабатывает null, а здесь null невозможен) — применяй и поясни в отчёте почему.
Отличие проявляется — не применяй, а опиши в отчёте, в чём разница.
B. Упрощение
Лишние абстракции. Интерфейс, базовый класс, фабрика, стратегия или DI-токен с одной реализацией. Дженерик-параметры, которые никогда не меняются. Опции и флаги, которые никто не передаёт. Слой, который только проксирует вызов. Класс без состояния с одним методом там, где проект пишет функции.
Защитный шум. Без вопросов удаляй catch, который просто пробрасывает ошибку дальше, и проверки на null или тип, которые уже гарантируют строгие типы или вызывающий код (только внутри проекта, не на границе с внешним вводом). Повторную валидацию удаляй, если её уже сделали выше. Удаление catch, который глотает ошибку, или фолбэка, который подставляет значение, меняет поведение: такое только описывай в отчёте.
Лишний код. Обёртки, которые просто передают аргументы. Переменная, использованная один раз, если её имя ничего не объясняет. Мёртвый код: неиспользуемые функции, параметры, импорты, экспорты. Перед удалением проверь использования по всему репозиторию, включая динамические вызовы, строковые ссылки и публичный API. Закомментированный код, забытые отладочные print и console.log. Преобразования туда-обратно. else после return, === true, if (x) return true; else return false. Вложенные условия, которые разворачиваются ранним return. Ручные циклы, которые заменяются понятным встроенным методом. Дублирующиеся ветки. Хранимое состояние, которое вычисляется из другого состояния. Строки там, где в проекте есть enum или union.
Комментарии. Удаляй комментарии, которые пересказывают код, нумеруют шаги, повторяют сигнатуру в docstring, рассказывают историю правок («исправлено», «новая версия») или ссылаются на задачу или вызывающего («добавлено для тикета 123», «используется в X»). Оставляй комментарии, которые объясняют, почему так сделано: скрытые ограничения, инварианты, обходные решения, ссылки на баги.
C. Уровень абстракции
Проверь, на правильном ли уровне сделано изменение:

Особый случай заплаткой у вызывающего вместо исправления в общей функции. Или наоборот: логика одного места затащена в общий хелпер под флагом.
Одна и та же правка скопирована в N вызывающих мест вместо одного места в вызываемой функции.
Логика не в том слое, если смотреть на архитектуру проекта: бизнес-логика в контроллере или компоненте, SQL в UI.
Код обходит собственную функцию проекта (подправляет результат после вызова), вместо того чтобы исправить её.
Обобщённый движок ради одного сценария.
Такие правки обычно затрагивают код вне diff или меняют структуру. Поэтому применяй их, только если они маленькие и целиком внутри diff. Иначе — предложение в отчёте.

D. Эффективность (только если код станет не сложнее)
Повторное вычисление в цикле. Тот же запрос или чтение файла несколько раз. N+1 при наличии batch-метода в проекте. Список строится ради первого элемента. Сортировка ради максимума. Лишние копии данных. Регулярка компилируется в цикле. Работа на горячем пути (рендер, каждый запрос), которую можно сделать один раз. Параллелить последовательные await и добавлять кеш нельзя молча: это меняет семантику ошибок и состояние. Такое только предлагай. Микрооптимизации пропускай.

E. Не как в проекте и вне задачи
Свой способ там, где в проекте есть принятый: прямой fetch вместо apiClient, print вместо logger, свой класс ошибки, чтение env в обход модуля конфига. Нейминг и раскладка файлов, отличающиеся от соседних.
Новая зависимость ради того, что уже есть в проекте или стандартной библиотеке. Предложи её убрать, но сам не убирай: это меняет lock-файл.
Работа вне задачи: правки в несвязанных файлах, попутный рефакторинг, фичи, о которых не просили. Только сообщай: удалив это, можно уничтожить работу, которую пользователь сделал намеренно.
Шаг 4. Разложи кандидатов
Применить — поведение проверено и идентично, правка внутри diff и делает код проще.
Предложить — поведение немного меняется, задет код вне diff, меняется API, крупная перестройка, возможная намеренная работа пользователя, удаление зависимости, недостаточная уверенность.
Отбросить — дело вкуса, мизерный выигрыш, то, что делает линтер или форматтер.
Баги — отдельно, не исправлять.
Шаг 5. Примени (кроме --dry-run)
Начинай с переиспользования (оно убирает больше всего кода), затем упрощение, затем комментарии.
Перед каждой правкой перечитывай файл: предыдущие правки сдвигают строки, а следующая находка может оказаться уже ненужной.
Правки минимальные, стиль форматирования сохраняй. Импорты, функции и типы, ставшие ненужными после твоих правок, удаляй, новые добавляй так, как принято в проекте (например, через алиасы @/). Файлы целиком не переформатируй. Форматтер запускай только на изменённых файлах и только если проект его использует (pre-commit, CI).
Шаг 6. Проверь
Найди команды проверок в scripts в package.json, Makefile, pyproject (pytest, tox, nox), в настройках CI (.github/workflows и подобных), в CLAUDE.md.
Порядок: сборка или тайпчек → линтер по изменённым файлам → тесты, связанные с изменёнными файлами → весь набор, если он быстрый (до ~3 минут) или связанных тестов нет.
Если проверка упала, выясни, твоя ли это правка. Падение в несвязанном месте, которое ты не трогал, вероятно было и раньше. Если виновата твоя правка, откати этот файл (git show <TREE>:<путь> > <путь>), прогони снова и перенеси находку в «Предложено». Тесты под правку никогда не подгоняй и проверки не отключай.
Если проверок нет или их нельзя запустить, скажи об этом в отчёте прямо. В этом случае оставь только тривиально безопасные правки: удаление мёртвого кода, комментариев и импортов, замену на идентичный хелпер. Остальное переведи в «Предложено».
Шаг 7. Отчёт
Пиши на языке пользователя. Свой diff получи снимком «после» (подставь хеш TREE из шага 1):

```bash

cd "$(git rev-parse --show-toplevel)" && GITDIR=$(git rev-parse --absolute-git-dir) && cp "$GITDIR/index" "$GITDIR/simplify.index"
AFTER=$(GIT_INDEX_FILE="$GITDIR/simplify.index" git add -A && GIT_INDEX_FILE="$GITDIR/simplify.index" git write-tree)
rm -f "$GITDIR/simplify.index"; echo "AFTER=$AFTER"; git diff --stat <TREE> "$AFTER"
## Simplify: <что упрощали>

Итого: применено N правок, −X/+Y строк · проверки: tsc ✓, eslint ✓, тесты 128/128 ✓

Большой diff: параллельные агенты
Если diff больше ~300 строк или 5 файлов и есть инструмент запуска агентов:

Шаги 1–2 сделай сам и составь бриф: хеши и команды diff, список файлов, инвентарь общего кода, ключевые зависимости и версия языка, соглашения, фокус пользователя.
Запусти в одном сообщении параллельно 3 агента, каждому передай бриф. Агенты только анализируют, правки запрещены: параллельные правки конфликтуют.
Переиспользование (агент Explore или general-purpose) — линзы A и E. Для каждой новой сущности он возвращает аналог (путь:строка) и отличия в поведении либо «аналогов нет» со списком того, что искал.
Упрощение и уровень (general-purpose) — линзы B и C.
Эффективность (general-purpose) — линза D. На небольшом diff объедини её со вторым агентом.
Каждое «это то же самое» от агентов проверь сам по шагу 4: агенты часто ошибаются в деталях поведения. Затем применяй правки сам, последовательно.
