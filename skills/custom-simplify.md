# /custom-simplify — упрощение без изменения поведения

Цель: изменённый код становится короче и понятнее, а ведёт себя ровно так же, как раньше.

У кода от моделей две типичные болезни. Первая — переизобретение: свой хелпер, тип, константа или обёртка над клиентом, хотя в проекте или зависимостях это уже есть. Вторая — перестраховка и «расширяемость»: лишние проверки, try/catch, абстракции на будущее. Скилл находит это, применяет безопасные правки, прогоняет проверки и отчитывается.

Это не поиск багов. Исправление бага меняет поведение, поэтому замеченный баг или уязвимость не исправляй, а вынеси в отчёт и предложи `/custom-code-review`. Если упрощать код с багом, баг может стать короче и начать выглядеть намеренным. Лучший порядок: `/custom-code-review` → исправление багов → `/custom-simplify` → тесты.

## Аргументы

`$ARGUMENTS` — текст после команды, в любом порядке:

- **Что упрощать.** Номер или URL PR, ветка, диапазон `A..B`, `staged`, пути к файлам. Без указания берутся все изменения текущей ветки относительно основной: коммиты, staged, unstaged и новые файлы.
- **`--dry-run`** (или «только отчёт») — ничего не менять, выдать отчёт с предлагаемыми правками.
- **Свободный текст** — фокус или ограничение («только переиспользование», «не трогай публичный API»). Он сужает линзы шага 3 и попадает в бриф агентам. Явное разрешение пользователя («API менять можно») сильнее умолчаний скилла.

## Принципы

Они важнее любого чек-листа ниже.

1. **Поведение не меняется.** Поведение — всё наблюдаемое: возвращаемые значения и их типы, выбрасываемые ошибки, побочные эффекты, их порядок и количество (запросы, записи, вызовы), публичный API, форматы сериализации, логи и метрики, на которые могут опираться алерты. Не уверен, что правка эквивалентна, — не применяй, а опиши.
2. **Лучшая правка — удаление.** Упрощение не добавляет новый слой. После правки кода меньше или столько же, но он проще.
3. **Понятность важнее краткости.** Никаких однострочников-головоломок, вложенных тернарников и цепочек из шести вызовов. Короче, но читать труднее — не делай.
4. **Как принято в проекте.** CLAUDE.md и соглашения соседнего кода сильнее общих идиом языка. Новый код выглядит так, будто его написал автор окружающего кода.
5. **Только изменённый код.** Область правок — добавленные и изменённые строки и новые сущности целиком. Нетронутые строки той же функции правь, только если без этого правка не складывается. Код вне diff не трогай. Исключение одно: ты переиспользуешь существующую функцию, и ей нужна крошечная обратно совместимая доработка (необязательный параметр), не влияющая на текущих вызывающих. Всё крупнее — предложение в отчёте.
6. **Правило трёх — для новых абстракций.** Не выделяй общую абстракцию, пока нет трёх копий; две похожие функции по пять строк — нормально. На переиспользование уже существующего кода правило не распространяется: оно оправдано с первого случая.
7. **Git пользователя неприкосновенен.** Правки только в рабочем дереве. Никаких `add`, `commit`, `stash`, `checkout`, `reset`, `push`.
8. **Ничего не придумывай.** «Код уже простой» — нормальный результат. Слабые находки ради объёма отчёта вредят.

## Шаг 1. Собери изменения и сделай снимок

Работай из корня репозитория. Если идёт merge, rebase или cherry-pick либо есть конфликты — скажи об этом и остановись. Команда находит базу и снимает состояние рабочего дерева вместе с новыми файлами, не трогая index и stash пользователя:

```bash
cd "$(git rev-parse --show-toplevel)" && GITDIR=$(git rev-parse --absolute-git-dir)
BASE=""; for b in "$(git symbolic-ref -q --short refs/remotes/origin/HEAD)" origin/main main origin/master master; do
  [ -n "$b" ] && git rev-parse -q --verify "$b^{commit}" >/dev/null && BASE=$(git merge-base HEAD "$b") && break; done
[ -z "$BASE" ] && BASE=$(git rev-parse HEAD) && echo "WARN: основная ветка не найдена, беру только незакоммиченное"
cp "$GITDIR/index" "$GITDIR/simplify.index" 2>/dev/null
TREE=$(export GIT_INDEX_FILE="$GITDIR/simplify.index"; git add -A && git write-tree)
rm -f "$GITDIR/simplify.index"; echo "BASE=$BASE TREE=$TREE"
git diff --stat "$BASE" "$TREE"
```

Запомни оба хеша: переменные между вызовами shell не сохраняются. Пустой `TREE` означает, что снимок не удался, — остановись. Если сработал WARN, упомяни это в отчёте.

`TREE` — снимок до твоих правок, он нужен при любой области. По нему в конце покажешь только свой diff и сможешь откатить файл: `git restore --source=<TREE> --worktree -- <путь>` (файл, которого в снимке не было, просто удали).

Что упрощаем:

| Область | Diff | Правки |
|---|---|---|
| по умолчанию | `git diff <BASE> <TREE>` | да |
| `staged` | `git diff --cached` | да, в рабочем дереве, без `git add` |
| `A..B` | `git diff A B` | да, если `B` — предок `HEAD` |
| ветка | `git diff $(git merge-base <основная> <ветка>) <ветка>` | только если это текущая ветка |
| PR | `gh pr diff <N>` | только если `gh pr view <N> --json headRefOid -q .headRefOid` равен `git rev-parse HEAD` |
| пути | diff по умолчанию, ограниченный путями; файл без изменений берётся целиком | да |

Где правки запрещены, работай как `--dry-run`. Если версия участка в рабочем дереве отличается от версии в выбранном diff (поверх staged есть unstaged, после `B` были коммиты), этот участок не правь, а вынеси в «Предложено».

Если это не git-репозиторий, упрощай указанные файлы, а перед правкой копируй каждый в `/tmp/custom-simplify/`. Если изменений нет, скажи об этом и остановись.

Не упрощай: lock-файлы, сгенерированный и вендоренный код, миграции, снапшоты тестов, строки локализации.

## Шаг 2. Узнай проект и сними baseline

Без этого шага дубль не распознать. Потрать на него время.

- **Правила.** CLAUDE.md, AGENTS.md, CONTRIBUTING в корне и в папках изменённых файлов.
- **Зависимости и версии.** Открой манифест (package.json, pyproject.toml или requirements, go.mod, Cargo.toml, Gemfile, composer.json, pom.xml или build.gradle). Если подключены, например, lodash, date-fns, zod, pydantic, more-itertools, guava, самописный аналог их функции — находка. Проверь версию языка и рантайма (engines, requires-python, target в tsconfig, версия go) и не предлагай то, чего в этой версии нет.
- **Общий код.** Найди папки вроде utils, helpers, lib, common, shared, core, hooks, constants, types, services, fixtures, factories и выпиши, что они экспортируют: `rg -n --no-heading "^(export |def |class |func |pub (fn|struct|enum) )" <папки>`
- **Соглашения.** Открой 1–2 соседних файла рядом с изменёнными: как там обрабатывают ошибки, логируют, ходят в HTTP и БД, называют вещи, раскладывают файлы, какие хелперы используют в тестах.
- **Изменённые файлы — целиком**, а не только hunks: правка должна вписываться в контекст.
- **Проверки и baseline.** Найди команды в scripts в package.json, Makefile, pyproject (pytest, tox, nox), CI (.github/workflows и подобных), CLAUDE.md. Если не `--dry-run`, прогони до правок тайпчек, линтер по изменённым файлам и связанные тесты и запиши, что уже падает. Иначе на шаге 6 не отличить свою поломку от чужой.

## Шаг 3. Найди кандидатов

Если diff больше ~300 строк или 5 файлов, см. «Большой diff» в конце.

### A. Переиспользование (главная линза)

Выпиши всё новое, что добавил diff: функции, методы, классы, хуки, компоненты, типы, константы, enum, регулярки, SQL, конфиги, обёртки над клиентами, тестовые фикстуры и хелперы. Для каждого ищи аналог:

- **По имени и синонимам:** format/fmt/render/stringify, parse/decode/deserialize, get/fetch/load/read, is/has/check/validate, make/create/build, normalize/clean/sanitize, map/convert/to, retry, sleep/delay/wait, chunk/batch, group/uniq, debounce/throttle.
- **По характерным литералам:** регулярки, форматы дат, тексты ошибок, URL и эндпоинты, имена полей, магические числа. Один литерал в двух местах почти всегда означает дубль.
- **По поведению:** опиши в двух словах, что делает код, и поищи эти слова в именах и комментариях.
- **В стандартной библиотеке и установленных зависимостях.**
- **По подозрительным именам:** V2, _new, Enhanced, Improved, utils2, новый файл рядом со старым похожим. Обычно надо было поправить старое, а не копировать.
- **Внутри самого diff:** одна и та же логика в двух новых местах. Объединяй, если одно место может просто вызвать другое или копия нетривиальна (от ~10 строк). Иначе действует правило трёх.
- **Инлайн-логика, которую закрывает существующий хелпер:** пути и URL, форматирование дат и денег, чтение env, самодельные type guard, retry, deep clone и merge, groupBy, chunk, uniq, плюрализация.
- **Типы:** новый интерфейс повторяет существующую модель, DTO или сгенерированный тип (OpenAPI, GraphQL, ORM). Используй его или выведи из него (Pick, Omit, Partial).
- **Константы:** магическое значение, которое уже есть в константах, enum или конфиге.
- **Тесты:** собственный setup при наличии общих фикстур и фабрик.

Найдя кандидата, открой его и сравни поведение: аргументы и значения по умолчанию, обработку null и пустых значений, бросает он ошибку или возвращает её, sync или async, часовой пояс и локаль, мутирует данные или копирует, побочные эффекты (логи, метрики, кеш).

- Поведение идентично — применяй.
- Отличие есть, но здесь не проявляется (хелпер обрабатывает null, а здесь null невозможен) — применяй и поясни в отчёте почему.
- Отличие проявляется — не применяй, опиши разницу в отчёте.

### B. Упрощение

- **Лишние абстракции.** Интерфейс, базовый класс, фабрика, стратегия или DI-токен с одной реализацией. Дженерик-параметры, которые никогда не меняются. Опции и флаги, которые никто не передаёт. Слой, который только проксирует вызов. Класс без состояния с одним методом там, где проект пишет функции.
- **Защитный шум.** Без вопросов удаляй catch, который просто пробрасывает ошибку дальше. Проверки на null или тип удаляй, если их гарантирует вызывающий код: все вызывающие внутри проекта, и ты их проверил. Статические типы без проверки вызывающих — не гарантия, а на границе с внешним вводом (HTTP, env, файлы, БД, JSON) проверки оставляй. Повторную валидацию удаляй, если её уже сделали выше по тому же пути. Удаление catch, который глотает ошибку, или фолбэка, который подставляет значение, меняет поведение: только описывай.
- **Мёртвый код, добавленный в diff.** Неиспользуемые функции, параметры, импорты, экспорты. Перед удалением проверь использования по всему репозиторию, включая динамические вызовы, строковые ссылки и публичный API. Код вне diff, ставший мёртвым из-за diff, — в «Предложено».
- **Отладочные остатки.** Закомментированный код, забытые print и console.log — если это явно отладка, а не штатный вывод программы или лог, принятый в проекте.
- **Лишний код.** Обёртки, которые просто передают аргументы. Переменная, использованная один раз, если её имя ничего не объясняет. Преобразования туда-обратно. else после return, `=== true`, `if (x) return true; else return false`. Вложенные условия, которые разворачиваются ранним return. Ручные циклы, заменяемые понятным встроенным методом. Дублирующиеся ветки. Хранимое состояние, вычислимое из другого состояния. Строки там, где в проекте есть enum или union.
- **Комментарии.** Удаляй те, что пересказывают код, нумеруют шаги, повторяют сигнатуру в docstring, рассказывают историю правок («исправлено», «новая версия») или ссылаются на задачу или вызывающего («добавлено для тикета 123», «используется в X»). Оставляй объясняющие, почему так сделано: скрытые ограничения, инварианты, обходные решения, ссылки на баги.

### C. Уровень абстракции

- Особый случай заплаткой у вызывающего вместо исправления в общей функции. Или наоборот: логика одного места затащена в общий хелпер под флагом.
- Одна и та же правка скопирована в N вызывающих вместо одного места в вызываемой функции.
- Логика не в том слое по архитектуре проекта: бизнес-логика в контроллере или компоненте, SQL в UI.
- Код обходит собственную функцию проекта (подправляет результат после вызова), вместо того чтобы исправить её.
- Обобщённый движок ради одного сценария.

Такие правки обычно затрагивают код вне diff или меняют структуру. Применяй их, только если они маленькие и целиком внутри diff. Иначе — предложение.

### D. Эффективность (только если код станет не сложнее)

Повторное вычисление в цикле. Тот же запрос или чтение файла несколько раз. N+1 при наличии batch-метода в проекте. Список строится ради первого элемента. Сортировка ради максимума. Лишние копии данных. Регулярка компилируется в цикле. Работа на горячем пути (рендер, каждый запрос), которую можно сделать один раз.

Применяй, только если убираемый повтор чистый: без побочных эффектов и с тем же результатом при каждом вызове. Сокращение числа запросов, параллелизация последовательных await и кеш меняют побочные эффекты, семантику ошибок и состояние — только предлагай. Микрооптимизации пропускай.

### E. Не как в проекте и вне задачи

- **Свой способ там, где есть принятый:** прямой fetch вместо apiClient, print вместо logger, свой класс ошибки, чтение env в обход модуля конфига. Принятый способ почти всегда ведёт себя иначе (ретраи, заголовки, формат лога, тип ошибки), поэтому по умолчанию это предложение. Применяй, только если сравнил и разницы нет.
- **Нейминг и раскладка файлов**, отличающиеся от соседних. Локальные имена внутри diff правь, экспортируемые и файлы — предлагай.
- **Новая зависимость** ради того, что уже есть в проекте или стандартной библиотеке. Предложи убрать, сам не убирай: это меняет lock-файл.
- **Работа вне задачи:** правки в несвязанных файлах, попутный рефакторинг, фичи, о которых не просили. Только сообщай: удалив это, можно уничтожить намеренную работу пользователя.

## Шаг 4. Разложи кандидатов

- **Применить** — поведение проверено и идентично, правка внутри области и делает код проще.
- **Предложить** — поведение хоть немного меняется, задет код вне diff, меняется публичный API или формат данных, крупная перестройка, возможная намеренная работа пользователя, удаление зависимости, недостаточная уверенность. При сомнении между «применить» и «предложить» — предложить.
- **Отбросить** — дело вкуса, мизерный выигрыш, то, что делает линтер или форматтер.
- **Баги и уязвимости** — отдельно, не исправлять.

## Шаг 5. Примени (кроме --dry-run)

- Порядок: переиспользование (убирает больше всего кода), затем упрощение, затем комментарии.
- Перед каждой правкой перечитывай файл: предыдущие правки сдвигают строки, а следующая находка может оказаться уже ненужной.
- Правки минимальные, форматирование сохраняй. Импорты, функции и типы, ставшие ненужными после твоих правок, удаляй; новые импорты добавляй, как принято в проекте (например, через алиасы `@/`).
- Удалил сущность из diff — удали и её собственные тесты, если они тоже из diff, и напиши об этом в отчёте. Остальные тесты не трогай.
- Файлы целиком не переформатируй. Форматтер запускай только на изменённых файлах и только если проект его использует (pre-commit, CI).

## Шаг 6. Проверь

- Порядок: сборка или тайпчек → линтер по изменённым файлам → тесты, связанные с изменёнными файлами → весь набор, если он быстрый (до ~3 минут) или связанных тестов нет.
- Сравни с baseline. Падало и раньше — не твоё, упомяни в отчёте. Новое падение — откати этот файл (`git restore --source=<TREE> --worktree -- <путь>`), прогони снова и перенеси находку в «Предложено». Тесты под правку не подгоняй, проверки не отключай.
- Перечитай свой diff целиком (команда из шага 7). Каждый hunk должен соответствовать находке из отчёта и лежать в области правок. Лишнее откати.
- Если проверок нет, их нельзя запустить или изменённый код ими не покрыт, скажи об этом прямо. Оставь только тривиально безопасные правки: удаление мёртвого кода, комментариев и импортов, замену на идентичный хелпер. Остальное переведи в «Предложено».

## Шаг 7. Отчёт

Пиши на языке пользователя. Свой diff получи снимком «после» (подставь хеш `TREE`):

```bash
cd "$(git rev-parse --show-toplevel)" && GITDIR=$(git rev-parse --absolute-git-dir)
cp "$GITDIR/index" "$GITDIR/simplify.index" 2>/dev/null
AFTER=$(export GIT_INDEX_FILE="$GITDIR/simplify.index"; git add -A && git write-tree)
rm -f "$GITDIR/simplify.index"; echo "AFTER=$AFTER"; git diff --shortstat <TREE> "$AFTER"
```

## Большой diff: параллельные агенты

Если diff больше ~300 строк или 5 файлов и есть инструмент запуска агентов:

1. Шаги 1–2 сделай сам и составь бриф: хеши и команды diff, список файлов, инвентарь общего кода, ключевые зависимости и версия языка, соглашения, фокус пользователя, принципы 1, 5 и 6.
2. Запусти в одном сообщении параллельно 3 агента, каждому передай бриф. Агенты только анализируют, правки запрещены: параллельные правки конфликтуют.
   - **Переиспользование** (Explore или general-purpose) — линзы A и E. Для каждой новой сущности: аналог (`путь:строка`) и отличия в поведении либо «аналогов нет» со списком того, что искал.
   - **Упрощение и уровень** (general-purpose) — линзы B и C.
   - **Эффективность** (general-purpose) — линза D. На небольшом diff объедини со вторым агентом.
3. Формат находки от агента: `путь:строка` · линза · что заменить на что · отличия в поведении · уверенность (высокая/средняя/низкая) · задевает ли код вне diff.
4. Каждое «это то же самое» проверь сам по шагу 3A и разложи по шагу 4: агенты часто ошибаются в деталях поведения. Убери дубли между агентами. Затем применяй правки сам, последовательно.
